# Changelog

All notable changes to `reasoning-dataset-lab` are documented here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project follows
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased

### Added

- `scripts/colab/local_boot_gatekeeper.py` runs the boot gatekeeper as the VM does (same subprocess script, prompts, judge and real transport) against a local HF home on a GPU, prints each prompt's output hash and whether it matches the goldens for `--card-type`, and writes a JSON receipt; it refuses a CPU device or a host with no visible NVIDIA GPU before any model load.
- **Lock-check window for the judge bake-off** (#66). `scripts/colab/launch_judges.sh --lock-check` (A100) and `--lock-check-stub` (CPU) take two separate inputs, `--anchor-items` (the 50 anchor items from the counted part) and `--p0a-items` (the 114 burned pilot items), plus one counted source, `--counted-items` or `--counted-manifest`. The window records the boot gatekeeper goldens (`boot_gatekeeper_goldens.filled.json`), runs the five judges over the anchors, writes `golden_anchor_manifest.json` and a `shard_manifest.json` built from the full counted part, runs P0a (`p0a_report.json`), and records the input hashes in `window.json` and `vm_receipt.json`. Both input sets are checked before a session opens and deleted on the VM after the run.
- **The free gate before any paid counted or time-one window.** Two tests, `test_e2e_fake_real_mode_time_one_reaches_judges` and `test_e2e_fake_real_mode_counted_reaches_judges` (`tests/test_colab_judge_launcher.py`, run by the normal pytest step of every CI job), drive the real `launch_judges.sh` live path in real `--time-one` and `--counted` mode against the fake `colab` CLI: launch, staging, upload, VM `main` with every preflight, venv sync / device / GPU gate / weights (their dryrun behaviour), and into the judge step, which must return judge rows for items of the window. The run must close with its receipts, the session stopped, and the uploaded items and part manifest deleted and listed. The VM cell runs through `tests/fixtures/fake_vm_real_mode_shim.py` (fake CLI hook `FAKE_COLAB_REAL_MODE_SHIM`), which strips every test hook from the VM environment, runs the GPU, network and venv steps as dryrun and runs the judge children with `--stub` and a stub window mode (so they are not in real mode); the fake kernel's `disk_usage`, `which('uv')`, `subprocess.run` and `huggingface_hub` patches stay active. It does not prove the judge child's real-mode checks, the boot gatekeeper's golden comparison, the weight SHA-256 checks or anything only a GPU VM shows; the first paid time-one window is the rung for those. Both tests must pass before a paid counted or time-one window is booked.
- `scripts/colab/promote_goldens.py` checks a window's filled boot gatekeeper goldens and writes a candidate `boot_gatekeeper_goldens.json` outside every git work tree, for review.
- New refusals from #66: `PART_MANIFEST_MISSING` (real mode never synthesizes a part manifest), `PART_MANIFEST_INVALID` (a part manifest that does not parse, is not an object or has no `part_id`), `PART_MANIFEST_SYNTHESIZED` (a leftover stub manifest in real mode), `COUNTED_ITEMS_REQUIRED` (a counted manifest with no real `items.jsonl`), `LOCK_CHECK_COUNTED_SOURCE_INVALID` (both counted sources given, or a counted source that does not match its manifest) and `SHARD_MANIFEST_GOLDEN_SHA_MISMATCH` (the golden file does not match the SHA-256 recorded in the shard manifest).

### Changed

- The shard manifest and the receipts record the golden anchor manifest's file SHA-256 as `golden_anchor_manifest_file_sha256` (#66). The golden file's own `golden_anchor_manifest_sha256` is its body hash and keeps its name.

### Fixed

- **Every downloaded judge's receipt is checked before any spend** (#71 review). Only the gatekeeper judge's receipt was checked before the session opened, and only for presence: a receipts directory without mu-judge's receipt passed `--dry` and the VM refused `BAKEOFF_JUDGE_RECEIPT_NOT_FOUND` only after the weight download. Now the static receipt checks the post-download verify runs (present, valid JSON with a `files` mapping, `repo` and `revision` equal to the pin; one shared function, `check_judge_receipt_static`) run for every judge in the download/verify set in the launcher before any `colab` call (`--dry` prints a `[receipts]` line) and in VM `main` before venv sync, with the same codes (`BAKEOFF_JUDGE_RECEIPT_NOT_FOUND` / `_INVALID` / `_MISMATCH`); the plan records `receipts_preflight`.
- **`local_boot_gatekeeper.py --out` can no longer overwrite repository files.** An `--out` inside the git repository (e.g. `scripts/colab/boot_gatekeeper_goldens.json`) is refused before anything runs, and an existing file is refused unless `--overwrite` (`LOCAL_GATEKEEPER_OUT_REFUSED`).
- **The success receipt records the card it ran on.** `vm_receipt.json` said `"hardware": "A100"` for every real time-one, counted and lock-check run; it now records the forwarded card type checked against `nvidia-smi` (`hardware`, e.g. `A100-80` or `L4`), the `nvidia-smi` GPU name (`gpu_name`) and `hardware_source`; stub and synthetic runs record `CPU` as before.
- **The boot gatekeeper's subprocess timeout is 300 s (was 120 s) and its phases are timed.** It covers torch import, `verify_ready` re-hashing the ~8 GB judge, the model load and two generations. The subprocess reports `phase_seconds` (`torch_import`, `verify_ready`, `model_load`, `generation_1`, `generation_2`, `total`) and writes one `BOOT_GATEKEEPER_PHASE` stderr line per phase as it ends (so a timeout's tail shows how far it got); the parent adds the measured `subprocess_elapsed_seconds` and the timeout. They are recorded as `subprocess_timings` in the gatekeeper report (in `vm_receipt.json` and `status.json`), and `local_boot_gatekeeper.py` writes them to its receipt and prints a `timings` line.
- **GitHub tokens are scrubbed.** `scrub_log_text` (used on every subprocess tail copied into `status.json`, receipts and `vm.log`) and the launcher's `scrub_stream` now redact `ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`/`github_pat_` tokens and `GITHUB_TOKEN=`/`GH_TOKEN=` values, as they already did HF, OAuth, JWT and colab proxy tokens.
- **A free rung on the real staged inputs.** `test_real_inputs_rung_time_one_mu_judge_gets_through_item_loading_and_scheduling` (opt-in: `RDLAB_REAL_RUNG_ITEMS` and `RDLAB_REAL_RUNG_PART_DIR`; skipped when unset, as in CI) runs the fake real-mode time-one window with `RDLAB_ONLY_JUDGES=mu-judge` on the real projected pilot items (pinned by SHA-256) and the real part's `part.json` and `checksums.txt`, so the judge child's item loading and scheduling checks run on real items before a paid window.
- **The boot gatekeeper's judge is always downloaded and verified** (timeone-mu, 2026-11-06). With `RDLAB_ONLY_JUDGES=mu-judge` the weight step fetched only mu-judge, then the boot gatekeeper loaded its own judge (`nemotron-3-nano-4b`, the goldens' `judge_id`) and `verify_ready` raised `RdlabError [BAKEOFF_JUDGE_SNAPSHOT_NOT_FOUND]`, after the paid setup. Now every real `--time-one`, `--counted` and `--lock-check` window adds the gatekeeper's judge to the download/verify set (once), records it as `boot_gatekeeper_judge` in `vm_receipt.json` and `status.json` (not a timed judge: `judge_order`, `only_judges` and the timing outputs stay as requested), and `--dry` prints the set as a `[judges]` line. New refusal `BOOT_GATEKEEPER_JUDGE_NOT_DOWNLOADED` (the goldens name no pinned judge, the judge is not in the set, or the weight step returned without it verified); it and `BOOT_GATEKEEPER_RECEIPT_MISSING` are now checked in the launcher before the session opens and in VM `main` before venv sync. Counted and lock-check windows always download all five judges, so they were not exposed.
- **A subprocess refusal keeps the exception.** The boot gatekeeper's reason kept the first 240 characters of the traceback, so the exception line was lost. Refusals from VM subprocesses now carry the last 40 lines of stderr (stdout when stderr is empty), scrubbed, and the exception line: `failure_output_tail` and `exception_line` in `status.json` and `vm_receipt.json` (the gatekeeper's reason and detail include both), and `VM_RUN_REFUSED`, `VM_REFUSAL_EXCEPTION` and `VM_REFUSAL_OUTPUT_TAIL` lines in `vm.log`. The gatekeeper now logs its judge, start and outcome (`VM_BOOT_GATEKEEPER_JUDGE` / `_START` / `_END`) and its subprocess to `vm.log`, and a gatekeeper subprocess timeout is a `BOOT_GATEKEEPER_SUBPROCESS_FAILED` refusal instead of an unexpected error.
- **A time-one window records the boot gatekeeper instead of comparing it.** A real time-one refused `BOOT_GATEKEEPER_GOLDEN_MISSING` after the gatekeeper ran, because the repo's goldens are unfilled, so no time-one could pass. Now time-one runs the gatekeeper in record mode: it writes `boot_gatekeeper_goldens.filled.json` (the lock-check format) to the run dir, compares nothing, and the receipt, `status.json` and `time_one_summary.json` say `gatekeeper: recorded, not compared` with the card type and the recorded hashes. Counted windows still compare and refuse, and the counted "no golden for this card" refusal (`BOOT_GATEKEEPER_GOLDEN_MISSING`) now fires before any paid step: in the launcher before the session opens and in VM `main` before venv sync. Lock-check is unchanged; no window writes `scripts/colab/boot_gatekeeper_goldens.json` (promotion stays `promote_goldens.py`). The real-mode shim's gatekeeper follows the same rule per mode.
- **The card type comes from the opened session, never a default.** The VM's gatekeeper used `A100` when no card type was given. Now the launcher reads the opened session's `Hardware:` and `Shape:` from `colab sessions` after `colab new` (an explicit table, each entry pinned to a receipt pairing the same window's session row with its nvidia-smi card: A100 Standard -> `A100`, A100 High-RAM -> `A100-80`, G4/L4/T4 Standard; anything else unknown) and forwards it as `RDLAB_CARD_TYPE` (not the `--gpu` request); an unknown value is refused `CARD_TYPE_UNKNOWN` right after open, before the alive probe, gate, uploads and exec. VM `main` checks it against `nvidia-smi --query-gpu=name` before venv sync (`CARD_TYPE_UNKNOWN`, `CARD_TYPE_MISMATCH`) and records `card_type_check`. Stub/dryrun keep a labelled default. The fake's sessions now use the real row shape (`Hardware: ... | Shape: ... | Variant: ...`) and its nvidia-smi answers `--query-gpu=name`.
- **The pinned-uv tests no longer race.** They shared `/tmp/uv-pinned` across xdist workers (and with any other suite on the host); each now uses its own directory through the test hook `FAKE_COLAB_PINNED_UV_DIR` (refused in real modes).
- **The fake VM learns the gatekeeper's contract.** The real-mode shim's gatekeeper refuses `BOOT_GATEKEEPER_SUBPROCESS_FAILED` when its judge was not among the downloaded and verified judges; `test_e2e_fake_real_mode_time_one_only_mu_judge` runs the timeone-mu invocation through the free gate.

- **Real time-one and counted windows read the part's own files, and the items are bound to them.** A part built by this repo holds `checksums.txt`, `items.jsonl`, `part.json` and `provenance.jsonl`; no builder writes a part `manifest.json`, yet the launcher and VM (#66-#69) looked only for one, so every real window on a real part refused `PART_MANIFEST_MISSING`, and a hand-written manifest of another part was accepted with nothing tying it to the items. Now:
  - `launch_judges.sh --part-dir DIR` (`RDLAB_PART_DIR`; default the items file's directory) names the part. Before any `colab` call (`--dry` and live), `part.json` must match the repo's part schema and hash to its `checksums.txt` line, the part's `items.jsonl` must hash to its line and hold `items_count` rows, and every uploaded row must equal the part row with the same id (`id`, `material`, `claim`). A counted window uploads the whole part in order; a time-one window any subset. `part.json` and `checksums.txt` are staged byte-identical beside `items.jsonl`; no `manifest.json` is read or written for these windows any more.
  - VM `main` runs the same function at `verify_part_manifest` before any paid step (identity, unique ids and the count rule; the VM has only the projected items), deletes the staged files after the run and lists them. Stub windows without a part get an in-memory stub identity; nothing is written, so the stub-manifest cleanup is gone.
  - New refusal `PART_MANIFEST_ITEMS_MISMATCH` (names the field that disagrees, never item text). `PART_MANIFEST_MISSING`, `PART_MANIFEST_INVALID` and `PART_MANIFEST_SYNTHESIZED` now refer to `part.json` and `checksums.txt`.
  - Receipts and `time_one_summary.json` record `part_identity` (real `part_id`, `items_count`, `part_json_sha256`, `items_jsonl_sha256`, binding rule) instead of `part_manifest`.
  - The pilot mass check in a time-one window runs on the burned pilot part named by its `part.json` and `items.jsonl` SHA-256, not by a label, and records the real `part_id` (`bakeoff-d-t10-sealed`) and hashes. **Receipts written before this change carry `part_id` `"pilot-40b"` for that part:** a label the VM made up; the part's real `part_id` is `bakeoff-d-t10-sealed`. Lock-check windows are unchanged and still use the `pilot-40b` allow-set for P0a.
- **The free e2e gate runs on a real part and cannot read the host.** The time-one and counted gate tests now build their part with the real part builder (no hand-written `manifest.json`) and pass `--part-dir`. The fake VM cell runs under an audit-hook guard that refuses reads under the test's temp root and the repo checkout outside the fake VM root, and the VM's weight cache is its own copy inside that root (the forwarded local `HF_HOME` is replaced). A new test forwards a local goldens path and a local `HF_HOME` to the cell and requires the window to fail naming the path. The shim's description now says what it replaces (including the judge child run with `--stub` and a stub window mode, and the kernel patches that stay active) and what the gate does not prove.

- A lock-check run given `--counted-manifest` (the launcher passes it as `RDLAB_COUNTED_MANIFEST`) no longer refuses `LOCK_CHECK_COUNTED_SOURCE_INVALID` after the venv, device and weight steps: VM `main` handed the manifest to the pipeline as an items source.
- VM `main` checks the counted source whenever one is given, in every mode, before the shard manifest is written and before venv sync, weight download or any device step. A counted manifest that is not valid JSON refuses `LOCK_CHECK_COUNTED_SOURCE_INVALID` instead of raising a raw error. `launch_judges.sh --dry` now resolves a `--counted-items` source as the live path does, not only `--counted-manifest`.
- The judge pipeline refuses a missing or invalid part manifest and a missing judge venv before it writes `shard_manifest.json` into the run directory, and a built shard manifest whose SHA-256 does not match the expected one is refused before it is written.
- A failure to delete the leftover part manifest is recorded in the receipt when the pipeline itself refused, not only when it finished, without changing the refusal. When both cleanup steps fail on the same file, the receipt lists it once.
- **Real time-one and counted windows no longer refuse `PART_MANIFEST_MISSING` after their paid steps.** The launcher staged only `items.jsonl` into `/content/rdlab_items`, never the part's own `manifest.json`, and the VM checked the part manifest only in the pipeline body, after venv sync, the device check, the GPU gate and the weight download. Every real counted or time-one window would have spent its setup and then refused. Now:
  - `launch_judges.sh` (`--dry` and live) checks the `manifest.json` beside the items file with the VM's own rules (`vm_judges.preflight_part_manifest`: the upload key/sealed guard, then parses, is an object, has a non-empty string `part_id`, is not a synthesized stub) and stages it, as given, to `/content/rdlab_items/manifest.json`. A real time-one or counted launch with no part manifest refuses `PART_MANIFEST_MISSING` before any `colab` call; an invalid one refuses `PART_MANIFEST_INVALID`, a stub one `PART_MANIFEST_SYNTHESIZED`. Nothing ever creates one.
  - VM `main` runs the same check as a preflight (step `verify_part_manifest`) right after the items allow-list, before the shard manifest, venv sync, the device/GPU gate and the weights. The pipeline body keeps its check as a second line. The staged manifest is deleted after the run (or the refusal) and listed in `deleted_items_receipt` with the other uploaded item files.
  - Lock-check windows (`--lock-check`, `--lock-check-stub`) do not need the items file's part manifest and are unchanged: they judge the anchor and P0a inputs, and their counted source is checked by the counted-source preflight (`--counted-manifest`, or the `manifest.json` beside `--counted-items`). Stub and dryrun windows may still run without one; the pipeline then writes a labelled stub manifest, as before.
- `launch_judges.sh --dry` now runs the lock-check two-input check (`bakeoff_judge.verify_lock_check_two_inputs`) and requires both `--anchor-items` and `--p0a-items`, as the live path does before the session opens, so `--dry` refuses whatever live refuses. Its comment claimed it already did.

## [0.5.0] - 2026-11-05

**The judge bake-off: build a sealed test part, run five local judges on it, score them without anyone seeing the keys first, and run the judges on Colab.** Tests: 1,162 passing, 2 skipped.

### Added

- **`rdlab bakeoff-part`** builds the writer-only Kind-D (T10) judge bake-off part from certified value sets, into an output directory outside the repo, with a sealed key store. `--resume` continues from a per-triad sealed checkpoint. `--construction anchored-two-hop` builds the anchored two-hop variant (domains, closures, entities and anchors rotate).
- **`rdlab bakeoff-probe`** runs the out-of-fold shortcut probe and the role and closure class-share gates on a part, so a part whose answers can be guessed from surface features fails before any judge sees it.
- **`rdlab bakeoff-judge`** runs one judge over the part's items without opening the sealed store, then closes its outputs into `outputs-closed.json`.
- **`rdlab bakeoff-judge-score`** verifies the closed outputs, joins them with the sealed keys, and writes sealed per-row records plus public aggregates. It refuses rows without timings (`BAKEOFF_SCORE_MISSING_ROW_SECONDS`) and parts that mix sources (`BAKEOFF_SCORE_MIXED_PART`).
- **`rdlab bakeoff-canary-tolerance`** measures the empirical log-prob drift of a 10-item canary set over repeated runs, and **`rdlab bakeoff-logprob-mass`** checks that yes/no probability mass covers at least 0.99 for binary calls.
- **Winner selection follows the pre-registration exactly.** No lenient fallbacks: explicit lower confidence bounds, per-class precision, pairwise rows, eligibility floors decided before the Holm candidate set, and registered domains only.
- **Colab launcher for the five-judge bake-off** (`scripts/colab/launch_judges.sh`). Each judge runs as its own subprocess in a hash-locked venv on CPython 3.15.1 with a pinned uv. The launcher checks the GPU, the disk and the device before any download, records step and per-judge timings with memory telemetry, caps spend from the live Colab rate, and stops its own session. Modes: `--session-smoke`, `--probe`, `--stub`, `--time-one`, `--counted` and `--dry`, plus `--resume` and `--until STEP` for stubs. Timing windows on A100s have run with it; see `REAL_SERVICE_ASSUMPTIONS.md` for what each real-service step relies on.
- New environment variables: `RDLAB_JUDGE_ORDER`, `RDLAB_FIRST_LOAD_JUDGE_ID`, `RDLAB_ONLY_JUDGES` and `RDLAB_FORCE_PINNED_UV`. `REQUEST_TIMEOUT` now defaults to 60 s.

### Experimental

- **Sharded counted windows** (`--shard k/n`, `--shard-manifest`, `--loop subblock|judge_outer`, `--subblock-items`, and `scripts/colab/merge_shards.py`). The merge refuses on any real-mode guard failure (including test hooks or overrides set in the environment), a determinism mismatch, a missing or changed golden anchor, missing ECC fields or any uncorrected ECC error, or verdict flips above the anchor budget, and it reports output-token drift as a warning. **No counted sharded run has completed yet.** The lock-check window that records the golden anchors is still in review and not in this release, so a counted run refuses at boot until it lands.

### Changed

- CI test legs time out at 25 minutes and run under pytest-xdist. Tests use committed fixtures instead of git history or the network.

### Changed

- **certify-values: `--reader-think FAMILY=SETTING`, `--parent-manifest PATH`, `rdlab pilot-b compare-arms`, and Nemotron pin `think="medium"`.** `rdlab pilot-b certify-values` gains repeatable `--reader-think FAMILY=SETTING` (`true`, `false`, `low`, `medium`, `high`, `max`) to override the pinned `think` for that reader family only (refusing unknown families or settings with exit code 2 before any Ollama call) and records `"think_overridden": true` on overridden reader rows. `--parent-manifest PATH` records `parent_manifest_sha256` (sha256 of the parent file's bytes) and `setting_tier` (e.g. `"nemotron:think=medium"`), refuses to overwrite the parent manifest or its companion review queue (`PILOT_B_CERT_PARENT_OVERWRITE_REFUSED`), and leaves `verify_manifest` verifying each addendum only as its own standalone manifest without merging verdicts across manifests. `rdlab pilot-b compare-arms PARENT ADDENDUM --reader nemotron --out PATH` writes a markdown comparison report with per-pair verdicts, a cross-table, exact-agreement counts, per-set reader pass at each setting, optional completion tokens and wall time, and length stops reported separately from verdicts (their own count per setting and their own row and column in the cross-table, never counted as a verdict or folded into disagree, with agreement rates labelled over all pairs and over pairs with a verdict at both settings). `DEFAULT_PILOT_B_MODEL_PINS["reader_1"]` (Nemotron) now pins `think="medium"` (citing Ollama v0.40.9 `model/renderers/nemotron3nano.go:30, 86-87`: `"medium"` is an effort hint the template knows, not a cap), while `verify_manifest` continues to accept r3's `think: true` manifest unchanged.

- **reader_3 (Mistral Small 3.2) answers directly (`think: false`); the manifest records each reader's think setting.** Mistral Small 3.2 has no thinking mode in Ollama, so a `think: true` request would fail on every call; the reader_3 pin now says `think=False`, and the adapter sends exactly the pin's setting (reader_1 and reader_2 keep `think: true`). The value manifest's reader rows gain `think`, and `verify_manifest` checks each recorded reader's `think` against its pin (a manifest that records none, or one that records a deliberating Mistral, fails). Manifests made before this change record no `think` and so fail the verifier until re-made; none is committed. `run_ollama_calibration_calls` takes the model's pinned `think` (it was hard-coded `true`), so calibrating Mistral sends `think: false`; an explicit value that differs from the pin is refused (`PILOT_B_CALIBRATE_THINK_OFF_FORBIDDEN` for a thinking model, `PILOT_B_CALIBRATE_THINK_MISMATCH` otherwise). The prompt, `PROMPT_SHA256`, `parse_answer`, `CONTROL_PAIRS` and the other pins are untouched.

- **Pilot A: the 12 floor and ceiling cells are buildable, on role-set d29499f.** `role-set` is re-pinned to `d29499f77a81bda144ebd51885f3c167a04667aa` (role-set #122; `pyproject.toml`, `uv.lock`, the adapter's `ROLE_SET_COMMIT`, the registry citation in `map.py`). The adapter no longer hard-codes the claim question: it reads the shortcut's `from` operator in role-set's `REGISTRY` and builds an exact (`=`) item with the claim question and a floor (`>=`) or ceiling (`<=`) item with the set question ("Which of them could be ...?"), because a claim cannot separate "at least k" from "exactly k" while the set of possible groups can. It filters the t10_variety catalogue by question, `ifs` and operator, and passes `target_shortcut` to `build_t10` for the set cells only; the exact cells keep the untargeted build, so their items and proofs are byte-identical to before (a pinned hash in the tests). A role-set without `target_shortcut` is refused when the generator is built (`ROLE_SET_PIN_LACKS_TARGET_SHORTCUT`). `examples/t10-pilot-a.map.yaml` now has 24 buildable cells (capacity 5 each) and no `role-set PR pending` cells; to keep its splits (train 48, eval 12) and shares, the 12 exact cells' targets are 3 (were 5) and the 12 new cells' targets are 2, total 60. The receipts of the exact cells name the new generator commit, which is the only field of theirs that changes.
- **certify-values: the licence-registry gate, a registry sha in the manifest, and a role fallback that refuses.** `rdlab pilot-b certify-values` now requires `--licence-registry <absolute path>` and, before any Ollama call, validates exactly the reader pins that will run against it, so a real certify-values run refuses (`PILOT_B_LICENCE_NOT_IN_REGISTRY`) when rnd's registry lacks a reader's licence entry (until now only `rdlab models --verify-live` did). The manifest records `licence_registry_sha256`, and `verify_manifest` requires it; `rdlab pilot-b verify-values-manifest --licence-registry <path>` recomputes it from the file. `OllamaBlindReaderAdapter` built without a role now maps the model family to its role (nemotron to reader_1, granite to reader_2, mistral to reader_3) and refuses any other family with `PILOT_B_UNKNOWN_READER_FAMILY`, instead of defaulting to reader_1. Earlier manifests carry no registry sha and no longer verify.

- **reader_3: Mistral Small 3.2 24B (Apache-2.0) as the c2 second-reader family; no run yet.** `DEFAULT_PILOT_B_MODEL_PINS` gains `reader_3` (`mistral-small3.2:24b`, manifest digest `5a408ab5...`), `rdlab pilot-b certify-values --readers` accepts `mistral`, and the manifest verifier allows a reader_3 that ran. A manifest made by the other two readers still verifies. The licence registry needs the entry `mistral-small-3.2-24b-hf-card`, so a real (non-stub) run refuses until rnd's registry carries it.

- **control pairs v2: six arguable pairs replaced; earlier control results don't carry over.** A control pair must be compatible beyond argument, so the six whose key a careful reader could rightly dispute (chromoly then ferritic steel, a carbide coating then ceramic, docked then moored, sealed then waterproof, acoustic then sonic, a dry gas seal then mechanical seal) are replaced by chromoly then alloy steel, an alumina coating then ceramic, a steel hull then metal, IP67 then dust-tight, R-134a then HFC-134a, and a silicon-carbide seal face then ceramic. The other fourteen, the 0.80 threshold and the pass rule are unchanged. The manifest records `control_pairs_sha256`, and `verify_manifest` recomputes it, so a manifest made under the old table fails verification.

- **certification asks its own question.** The first full run showed the triad blind-read prompt (does the claim follow from the material?) makes a reader answer "unsupported" to a compatible but unstated claim (ester then synthetic), so it cannot tell a contradiction from a gap. `rdlab pilot-b certify-values` now asks: "Statement 1: The <attribute> of <entity> is <v1>. Statement 2: ... Could both statements be true of the same <entity> at the same time?", answered with exactly one word, `compatible` / `incompatible` / `unsure`, parsed strictly (case and surrounding whitespace ignored; anything else is a parse error and counts toward the error stop). A pair is a contradiction only on `incompatible`; a control pair passes on `compatible` or `unsure`. The 20 control pairs are unchanged. Same pins, `think` on, `num_predict` 3072, `num_ctx` 4096. The manifest records the sha256 of the prompt text, and `verify_manifest` rejects a manifest made with any other prompt. `verify_manifest` also recomputes each reader's control passes from the pairs and enforces the 0.80 threshold itself, instead of trusting the recorded `passed`. The real reader adapter gains `chat_raw` for callers that build their own messages. The CLI no longer writes the manifest a second time.

- **generator: every categorical value set sits on one axis and its values exclude each other.** An unsupported claim swaps the true value for another from the same set, so it is a contradiction only if both cannot be true. An audit of all 50 value sets (10 domains x 5) found most of them mixed an axis (a material beside a type, a mode beside a sub-process) or held a class beside its member (`synthetic` beside `ester`, `mineral` beside `paraffinic`, `air` beside `nitrogen`, `grounded` in two transformer sets), which makes an `unsupported` claim true and its key wrong (Pilot B stub 10d). All 50 sets were rewritten as 5 values on one declared axis (`VALUE_SET_AXES`); the 10 state sets hold top-level operating modes only, and no value sits in two sets of a domain. Some attribute names changed with their axis (for example `grid status` is now `turbine mode`, `valve state` is `pump state`), so facts and tables generated from a seed differ from earlier builds. `VALUE_SUBSUMPTIONS` records the known overlaps as a regression lint, `EXCLUSIVE_BY_MEANING` the close pairs reviewed with a reason, and `tests/test_pilot_b_value_sets.py` fails on a covering value beside its member, on one value spelled inside another, and on a value in two sets of a domain.
- **The exclusivity guard is not enforced yet.** The lint above only catches overlaps someone has written down; new or replacement values get no protection from it. The enforcing guard is the certification below, and it does not switch on until the certification PR (the manifest from a real run on the readers, `is_disjoint_value` reading it, and a CI gate that every set is certified with a matching hash). Until then, do not read this change as protection it does not give.
- **value certification tooling, with no certification claimed.** `pilot_b/value_certification.py`: `rdlab pilot-b certify-values` asks two local reader families whether every directed pair in a set (20 for 5 values) reads as a contradiction, one reader loaded at a time, with `--num-ctx`, `--num-predict`, `--readers`, a calibration of the first calls that stops the run when the projected time passes `--wall-cap-s`, and an error-rate stop (`--error-rate-stop`, 2% by default). It writes a content-hashed manifest of the admitted sets and a review queue of the others. `rdlab pilot-b verify-values-manifest` loads a manifest and fails when any set is uncertified or its hash no longer matches. Tested with fake readers; no manifest is committed.
- **certification: provenance, partial results, unload.** `verify_manifest` now requires a complete run, at least two readers from distinct families whose name, digest and family equal the pinned reader models in `DEFAULT_PILOT_B_MODEL_PINS` (a fake reader cannot match), and verdict keys equal to the manifest's reader names. A run that stops (error rate, wall cap) writes its manifest marked `"complete": false` with the stop code, the review queue, and `<queue>.failures.jsonl` (reader, pair, done_reason, completion_tokens, the tail of the raw text, or the error code); every exit path unloads the reader it loaded; the calibration projection also runs when one reader's jobs equal `--calibration-calls`. Defaults `--num-predict 3072`, `--num-ctx 4096` (thinking tokens count against `num_predict`; measured up to 2,019 in stub 10d); `--num-ctx` is a cap.
- **certification: length routing and a negative control.** A `length` or `max_num_ctx_exceeded` stop means not certified: the pair goes to the review queue with its reason and the failing call is logged, but it does not count toward `--error-rate-stop`, which counts only transport and parse errors. Before its certification calls each reader answers 20 compatible pairs (a member then its class, a synonym, an implication) through the same prompt and settings; it passes with at least 16 of 20 answers that are not "unsupported" (`--control-pass-threshold`, default 0.80; length stops and errors fail). If a reader fails, the run certifies nothing: the manifest says `"control_failed": true`, every set goes to the review queue, and the reader is unloaded. `manifest["control"]` records each reader's passes, threshold and every pair's verdict, done_reason and tokens, and `verify_manifest` rejects a manifest with no passing control.
- **reports record the render-failure gate.** `pilot_b_report.json` carries `render_failure_rate` and `max_render_failure_rate` (schema updated).
- Four more sets re-cut after the Argon review: reactors/cladding metal, compressors/rotor coating, boilers/tube alloy, chillers/condenser cooling (they need re-certifying).
- **render: the value-before-entity check is dropped, and intervals may be written two ways.** One entity per sentence already stops a value binding to the wrong entity. An interval may be "between <lo> and <hi>" or "from <lo> to <hi>". The writer prompts ask for "between" and for a direct verb (is, operates in, uses, has) on exact facts, never a hedged link such as "characterized by" or "associated with".
- **gate: render failures are their own rate.** They no longer count against every verdict class: class rates are over the triads that rendered, and `max_render_failure_rate` (default 0.50) halts the build with `PILOT_B_RENDER_FAILURE_RATE_ABOVE_CEILING`.
- **`mutate_fact_value` refuses instead of falling back.** A value outside its own attribute's set raises `PILOT_B_NO_EXCLUSIVE_VALUE`; the cross-attribute swap and the `non-<v>` / `uncoated-<v>` strings are gone.

- **Python: `requires-python` is `>=3.13` (was `>=3.12,<3.13`); Python 3.12 is dropped.** 3.15 is the main target (`.python-version`); CI runs the suite on 3.15 (`test`, with the Atlas check), 3.13 (`test-py313`) and 3.14 (`test-py314`), each from `uv sync --frozen`. Coverage (floor 90) and a Codecov upload run on the 3.15 leg only; the 3.13 and 3.14 legs run the tests without coverage. Every action is pinned by commit SHA with a version comment, at its current major (checkout v7.0.1, setup-uv v10.3.2, setup-node v7.1.0, codecov-action v7.1.1, read 2026-10-25). `role-set` is re-pinned to its commit that supports `>=3.13` (`d105f3d`, role-set PR #121; to be re-pointed to the merge commit). The Part F parity test now expects `>=3.13`. On 3.15, PyYAML 6.0.3 installs from its source distribution until it publishes cp315 wheels.
