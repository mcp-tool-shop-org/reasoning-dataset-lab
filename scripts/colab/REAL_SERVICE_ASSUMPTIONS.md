# Real-Service Assumption Audit (`scripts/colab/launch_judges.sh` & `scripts/colab/vm_judges.py`)

This document audits every interaction the five-judge Colab launcher (`scripts/colab/launch_judges.sh` and `scripts/colab/vm_judges.py`) has with the `colab` CLI (`google-colab-cli` v0.7.4, captured in `tests/fixtures/colab_help.txt` and `tests/fixtures/colab-cli-contract.json`) and the remote Colab Jupyter/IPython runtime.

- **Total rows in assumption table:** **20**
  - **Fake now enforces:** **10**
  - **Left for the stub:** **9** (8 of which also have conservative **guards** in `tests/fixtures/fake_colab.py`, labelled below as guards rather than verified real-service behaviour)
  - **Probe answers it:** **1** (row 20: VM Python 3.15, `uv`, and `pyyaml==6.0.3` sdist build toolchain, answered directly by `--probe` / `RDLAB_STEP=probe` and preflighted at `--step gate` via `check_vm_python_preflight`)

## The part a window runs on

A sealed part built by this repo (`rdlab bakeoff-part`; `waves_and_sealing._PART_FILES`) holds exactly `checksums.txt`, `items.jsonl`, `part.json` and `provenance.jsonl`. No builder writes a part `manifest.json`; until this change the launcher and VM looked only for one, so a real time-one or counted window on a real part refused `PART_MANIFEST_MISSING` (before #66 the VM made up `{"part_id": "pilot-40b"}` instead).

- **What is read.** `launch_judges.sh --part-dir DIR` (`RDLAB_PART_DIR`) names the part; a real `--time-one` or `--counted` launch without it refuses `PART_MANIFEST_MISSING` before any `colab` call (`require_part_dir_for_mode` in `scripts/colab/launch_judges.sh`): the items file is a projection kept outside the part, so its own directory is never the part (stub and dryrun windows still default to it). The launcher (`check_part_manifest_beside_items` in `scripts/colab/launch_judges.sh`, `--dry` and live) runs `vm_judges.preflight_part_manifest` (`scripts/colab/vm_judges.py`) with the part's `items.jsonl` and the repo's part schema: `part.json` must parse, carry a non-empty `part_id` and a positive `items_count`, match `schema_check.validate(..., "part")`, and hash to the `part.json` line of `checksums.txt`; the part's `items.jsonl` must hash to its line and hold `items_count` rows, and every other file `checksums.txt` lists (`provenance.jsonl`) must hash to its line (`verify_part_files_against_checksums`, `scripts/colab/vm_judges.py`). It stages `part.json` and `checksums.txt` byte-identical to `/content/rdlab_items/` beside the uploaded `items.jsonl`.
- **The projection** is made by `rdlab bakeoff-project --part-dir <part> --out <file>` (`src/reasoning_dataset_lab/pilot_b/bakeoff_project.py`): `{id, material, claim}` for every item in the part's order, after checking `part.json` and `items.jsonl` against `checksums.txt`, with `<file>.sha256` beside it. It refuses to write inside the part directory or under any `sealed_store/` (`PROJECTION_OUT_FORBIDDEN`), over an existing file (`PROJECTION_OUT_EXISTS`), or from a part whose files no longer match `checksums.txt` (`PROJECTION_PART_INVALID`). The launcher's binding accepts exactly its output for a counted window. On the burned pilot it reproduces `colab-runs/inputs/pilot40b-items-projected.jsonl` byte for byte (SHA-256 `9bdeb527…`).
- **The binding rule** (`bind_items_to_part` in `scripts/colab/vm_judges.py`). The uploaded file is a projection (`{id, material, claim}`; the upload allow-list refuses a part's own rows). The launcher checks every uploaded row against the part row with the same id (`id`, `material`, `claim` equal), so the projection is verified, not trusted. A counted window (`counted`, `counted-stub`) must upload the whole part in the part's order; a time-one window any subset of it (the VM then takes the first `TIME_ONE_ITEMS_LIMIT` rows). A disagreement refuses `PART_MANIFEST_ITEMS_MISMATCH` naming the field (`items_count`, `id`, `id order`, `material`, `claim`, `items.jsonl sha256`), never the item text.
- **On the VM** (`main` step `verify_part_manifest` in `scripts/colab/vm_judges.py`, before the shard manifest, venv sync, device/GPU gate and weights) the same function runs without the part's items: it checks `part.json` against `checksums.txt`, the seal's shape, the pins, unique ids and the count rule. It does not run the schema check (the kernel imports nothing from the repo). The staged files are deleted after the run and listed in `deleted_items_receipt`.
- **Both checks are recorded, each labelled by where it ran.** The launcher writes its result to `launcher_part_binding.json` (`window_part` and, for a lock-check window, `p0a_part`: rule, counts, `projection_checked: true`, the part's `part.json` / `items.jsonl` / `checksums.txt` SHA-256 and the uploaded file's SHA-256; `launcher_binding_entry` in `scripts/colab/vm_judges.py`), keeps a copy in the out dir, logs a `PART_BINDING_LAUNCHER` line to `colab-cli.log`, puts it in `outcome.draft.json` (`launcher_part_binding`) and uploads it beside the items. The VM's own binding says `checked_by: "vm"` and `projection_checked: false` (it has only the projection); it carries the launcher's record into `part_identity.launcher_binding` after checking that the record names this part and this uploaded file (SHA-256 and count), else `PART_BINDING_RECORD_MISMATCH` (`attach_launcher_binding` in `scripts/colab/vm_judges.py`). Without a record (an in-process run) `launcher_binding` is `null`; the VM never sets `projection_checked` itself.
- **Recorded.** `time_one_summary.json` and `vm_receipt.json` carry `part_identity`: the real `part_id`, `items_count`, `part_json_sha256`, `items_jsonl_sha256` (the part's own items file, from `checksums.txt`), `checksums_sha256`, `is_pilot_40b`, `pin`, `pin_status`, `seal`, the VM's binding and the launcher's. Stub and dryrun windows without a part get an in-memory stub identity (`part_id` "stub"); nothing is written.

## The card type

- **Read from the opened session, never defaulted in a real mode.** After `colab new` the launcher reads the session's `colab sessions` row and maps its `Hardware:` AND `Shape:` through the explicit table `SESSION_CARD_TYPES` (`scripts/colab/vm_judges.py`): `Hardware: A100 | Shape: Standard` -> `A100` (40 GB), `Hardware: A100 | Shape: High-RAM` -> `A100-80` (`--high-mem`, the 80 GB card), `G4`, `L4`, `T4` with `Shape: Standard`; extra spaces are tolerated and anything else (CPU, TPUs `V5E1`/`V6E1`, an unseen card or shape) is refused `CARD_TYPE_UNKNOWN`. - **Checked on the VM before venv sync.** `verify_vm_card_type` (step `verify_card_type`) maps `nvidia-smi --query-gpu=name` through `GPU_NAME_CARD_TYPES` (`A100-SXM4-40GB` -> `A100`, `A100-SXM4-80GB` -> `A100-80`, `RTX PRO 6000` -> `G4`, `NVIDIA L4` -> `L4`, `Tesla T4` -> `T4`; the same names as the session table and the goldens' `card_types` keys) and refuses `CARD_TYPE_UNKNOWN` / `CARD_TYPE_MISMATCH`. nvidia-smi is the driver's binary on the GPU base image, so it needs no venv. ## The window's rate, at open and mid-run (2026-11-06)

`colab usage` prints `Usage rate: <float>/hr` and `Active assignments: <int>` for the whole account (every open
assignment), one per line. Until a new session registers, the service reports `Usage rate: 0.00/hr` with
`Active assignments: 0` (windowC2-12-t4-s1a-20261027: three such reads, then the T4's 1.07/hr with a count of 1).

- **At open** (`launch_judges.sh`, the post-open poll): the window rate is post minus pre, accepted from two agreeing
  reads (within 0.01) at the same count of at least 1, above the floor. A count of 0 or none before then is "not yet"
  and only uses up the poll budget (`LIVE_USAGE_RATE_UNAVAILABLE`).
- **Mid-run** (the cost-cap monitor, `scripts/colab/rate_rereads.py`): `colab usage` is re-read every
  `RDLAB_RATE_REREAD_SECONDS` (1 to 60, default 30) under `timeout -k`. Our rate is the account rate minus a
  neighbour baseline (first the pre-open rate). A count change is not judged until two reads at the new count agree;
  then baseline = account - the highest stable rate of ours seen. Only two agreeing reads at the settled count can
  raise our rate:
  the remaining runtime is repriced at max(`--max-rate`, highest stable rate seen), shorter, never longer, and a
  stable rate above `--max-rate` stops the window `RATE_ABOVE_MAX` (fetched and stopped as on a cost-cap stop). Three
  reads in a row with no count, a count of 0, no rate or an own rate below the card's floor stop it
  `ASSIGNMENTS_UNREADABLE`. Each read runs as a tracked background PID, killed by PID (with its children) by the
  monitor's trap and the teardown if the run ends while it is in flight. Each read is recorded in
  `rate_rereads.jsonl` and `outcome.draft.json` (`rate_rereads`), numbers and decisions only.
- **Known limits**, not chased: a neighbour opening in the exact read our own rate rises absorbs that rise into the
  baseline; a CLI outage of three or more reads ends the window early; a count that leads the rate by two or more
  reads can falsely trip.

The first directory in the bottom-up walk whose `memory.max` is a finite integer (`< 2^60`) sets `nearest_finite_path`, `nearest_finite_memory_max` (int), and `nearest_finite_memory_current` (`memory.current` at that path, or `null` if missing); if every level is `"max"` or missing, all three `nearest_finite_*` fields are `null`. Logged once in `gate_status.json` (`cgroup_limit_chain`), once at run start (`step_start` `unpack` in `progress.jsonl` and `vm_receipt.json`), and via `nearest_finite_cgroup_path`, `nearest_finite_memory_max`, and `nearest_finite_memory_current` on every `judge_download_start`, `judge_download`, `download_failed`, `judge_pass_done`, and `judge_failed` line in `progress.jsonl`.
7. **Per-judge weight download child subprocess (`src/reasoning_dataset_lab/pilot_b/judge_download.py:1-223`, `scripts/colab/vm_judges.py` (`download_all_judge_weights`)):**
   - `scripts/colab/vm_judges.py` is completely import-free of `huggingface_hub` (even lazily). Instead, `download_all_judge_weights` spawns `<venv>/bin/python -m reasoning_dataset_lab.pilot_b.judge_download` per judge in that judge's synced CPython 3.15 venv (`venv-d3` for `d3-mini`, `venv-judge` for the other four judges), followed immediately by parent `verify_snapshot_against_receipt`.
   - **Network and token split:** All five judge repositories (`flowaicom/Flow-Judge-v0.1`, `ibm-granite/granite-guardian-4.1-8b`, `nvidia/NVIDIA-Nemotron-3-Nano-4B-BF16`, `qybaihe/mu-judge-nemotron-nano-4b`, `vllm-sr/d3-mini`) are public, non-gated open-weights repositories. Therefore, `build_download_child_env` gives the download child network access (`HF_HUB_OFFLINE` unset) with no `HF_TOKEN*`/`HUGGING_FACE_HUB_TOKEN`, while `build_judge_child_env` runs the judge child completely offline (`HF_HUB_OFFLINE=1`) with no `HF_TOKEN*`/`HUGGING_FACE_HUB_TOKEN`.
   - **Version recording & verification:** Inside the download child, `detect_download_stack_versions` reads `huggingface_hub.__version__` and `hf_xet.__version__`, verifies they match the venv's lock (`venv-judge`: `huggingface-hub==2.4.0`, `hf-xet==1.8.0`; `venv-d3`: `huggingface-hub==1.33.0`, `hf-xet==1.8.0`), refuses with `DOWNLOAD_STACK_VERSION_MISMATCH` on mismatch, and records both versions in `download_done/<judge_id>.json`, the `judge_download` progress line, and `vm_receipt.json` (`gate_status.json` records `download_stack_versions.status = "not_available_at_gate_before_venv_sync"` with the expected lock versions because `--step gate` runs before repo upload and before `sync_judge_venvs` creates `venv-judge` and `venv-d3`).
   - **Download child timeout, process-group kill, and failure handling:** Each download child is bounded by `min(configured, remaining_wall - margin)` (`RDLAB_DOWNLOAD_CHILD_TIMEOUT_SECONDS` default `900.0` s, `RDLAB_CHILD_WALL_MARGIN_SECONDS` default `60.0` s); on timeout, `_run_child_with_group_timeout` kills the child's entire process group (`SIGTERM` -> `SIGKILL`), verifies no group/session member survived in `/proc` (`surviving_pids`, `any_member_survived`), reads post-kill `gpu_memory_used_mib` and `parent_rss_bytes`, and classifies the stop as `DOWNLOAD_CHILD_TIMEOUT`. Signal `9` (`SIGKILL`, `rc=-9`/`137`) without timeout or `oom_kill_delta > 0` classifies as `DOWNLOAD_CHILD_OOM`; any other non-zero exit or a missing/malformed `download_done/<judge_id>.json` classifies as `DOWNLOAD_CHILD_FAILED`; the parent survives, emits a `download_failed` progress line (including `elapsed_seconds`, `timeout_seconds`, `surviving_pids`, `any_member_survived`, `gpu_memory_used_mib`, `parent_rss_bytes`, nearest finite cgroup limit fields, and scrubbed `stderr_tail` `<= 4 KB`), and takes the normal stop path (`status.json`, `vm_receipt.json`, `result.tar.gz`, `run_end`, `rc=2`).
8. **Mid-run cost-cap stop and partial artifact fetch before `result.tar.gz` exists (`scripts/colab/launch_judges.sh` (`fetch_results_once`, `fetch_completed_judge_checkpoints`, cost-cap watcher loop)):**
   - While `colab exec` (`--step run`) is in flight on the VM, the rig's background cost-cap watcher (`COST_CAP_PID` in `scripts/colab/launch_judges.sh`) polls `elapsed_s = cur_epoch - OPEN_CLOCK_EPOCH` every `RDLAB_COST_CAP_POLL_SECONDS` (`default=1` s) against `COST_CAP_MAX_RUNTIME_SECONDS = ceil(CAP_UNITS * 3600 / LIVE_RATE_UNITS_PER_HOUR)`.
   - When `elapsed_s >= COST_CAP_MAX_RUNTIME_SECONDS` is reached mid-run before `/content/result.tar.gz` has been built on the VM, the cost-cap watcher writes `elapsed_s` to `$COST_CAP_MARKER`, logs `COST_CAP_REACHED` to `colab-cli.log`, calls `fetch_results_once "$WATCHDOG_FETCH_TIMEOUT"` (`scripts/colab/launch_judges.sh`) before terminating `EXEC_PID`, and stops the Colab session.
   - When `/content/result.tar.gz` does not exist yet on the VM, `fetch_results_once` fetches and scrubs in place:
     - **Progress:** `/content/rdlab_run/progress.jsonl` -> `<out_dir>/progress.jsonl` (`fetch_results_once` in `scripts/colab/launch_judges.sh`);
     - **Logs:** `/content/rdlab_run/logs/vm.log` -> `<out_dir>/logs/vm.log` (`fetch_results_once` in `scripts/colab/launch_judges.sh`), alongside `<out_dir>/colab-cli.log` (`log_msg` in `scripts/colab/launch_judges.sh`);
     - **Gate status:** `/content/gate_status.json` -> `<out_dir>/gate_status.json` (`fetch_results_once` in `scripts/colab/launch_judges.sh`), plus `/content/status.json` and `/content/rdlab_run/vm_receipt.json` if already written;
     - **Finished judges' done/rows:** `fetch_completed_judge_checkpoints` (`scripts/colab/launch_judges.sh`, called from `fetch_results_once`) inspects every `judge_pass_done` line in `<out_dir>/progress.jsonl` and, for each finished (judge, mode) pass (`vm_judges.launcher_completed_passes`, which names the files with `judge_done_filename_for_pass` and `rows_filename_for_pass` for every pass mode), runs bounded local verification (`timeout -k "$COLAB_KILL_GRACE_SECONDS" "$verify_timeout"`, default `30` s, inside `fetch_completed_judge_checkpoints`): on `rc=0` it clears any `.unverified_judge_done` entry and keeps the pair; on timeout (`rc=124` or `137`) it keeps the in-place pair on disk, records `judge_id\tpass_mode\tdone_file` in `.unverified_judge_done` (parsed via `run_records.read_unverified_passes` inside `write_outcome_draft` so unverified entries are excluded from `judges_completed` and listed in `outcome.draft.json["unverified_passes"]`, or `"unverified_passes_malformed": true` with `judges_completed: []` on error), and logs `FETCHED_PASS_VERIFY_TIMEOUT`; only a real verification failure deletes the stale pair. Both `merge_shards` (`MERGE_UNVERIFIED_PASS`, pre-checking all original and replacement shards before anchor loading or tombstone writes unless `--allow-unverified` in stub mode, which is refused with `TEST_HOOK_IN_COUNTED_MODE` in counted/real mode) and the scorers (`BAKEOFF_SCORE_UNVERIFIED_PASS`, `BAKEOFF_LOGPROB_MASS_UNVERIFIED_PASS`, `_checked_logprob_rows_dir` in `scripts/colab/vm_judges.py`) call `run_records.collect_run_unverified_passes` (refusing `.unverified_judge_done` entries, directory/symlink/unreadable/non-UTF-8/malformed markers, and `outcome.draft.json` `unverified_passes` / `judges_completed` mismatches, reporting partial rows missing from `judges_completed` as `rows present for a pass the outcome does not list as completed`; whitespace-only regular markers return `[]`); `vm_judges.py reverify-unverified <out_dir>` and `vm_judges.py exclude-incomplete <out_dir> --judge <id> --pass-mode <m>` (`scripts/colab/vm_judges.py` (`reverify_unverified`, `exclude_incomplete`)) refuse while a run is live (`outcome.draft.json` absent, `.rig_*` marker active, `.rig_launcher.pid` / `.rig_exec.pid` alive under POSIX/WSL, or `status.json` `running`), re-run `launcher_verify_fetched_pass(staged=False, want_sha256=<from progress.jsonl>)` offline without a tight timeout to prune verified entries (rebuilding candidates from marker + `progress.jsonl` on-disk files while skipping `excluded_incomplete_passes`, even after a stale `unverified_passes_malformed` flag), or move incomplete rows/pairs (requiring an explicit `judges_completed` string list and no `judge_pass_done` progress record) to `rows.incomplete/` and record `excluded_incomplete_passes` in `outcome.draft.json` (plus `amendments` in `outputs-closed.json`, `merge_receipt.json`, and the score report). Once the fetch deadline expires or `CLEANUP_SKIP_FETCH=1` (`fetch_halted=1` in `fetch_completed_judge_checkpoints`), all remaining passes are verified in one batched Python call (`vm_judges.write_launcher_halted_pass_verdicts` in `scripts/colab/vm_judges.py`, invoked inside `fetch_completed_judge_checkpoints` under one `timeout`, adding at most one `30 + COLAB_KILL_GRACE_SECONDS` s bound noted against `FETCH_STEP_BOUND_SECONDS` in `compute_cleanup_bounds`), deleting `BAD` pairs, counting `OK` pairs, and keeping+not-counting passes on batch timeout. Active re-fetches download `.part` files and run `vm_judges.launcher_verify_fetched_pass(..., staged=True)` to move them to `<out_dir>/judge_done/` (scrubbed in place inside `fetch_results_once`) and `<out_dir>/rows/` only when the rows' sha256 equals the judge_done `sha256`, otherwise deleting both staged `.part` files and any moved destination pair and logging `FETCHED_JUDGE_DONE_INVALID`, `FETCHED_ROWS_MISSING` or `FETCHED_ROWS_SHA_MISMATCH`. The early cleanup also deletes a `judge_done` / `rows` pair that is consistent with itself when the VM's latest `progress.jsonl` record for that pass differs; this is a deliberate fail-closed outcome.
   - Both the main cost-cap handler (`scripts/colab/launch_judges.sh`) and the `EXIT` trap (`stop_all` in `scripts/colab/launch_judges.sh`) record the cap stop in `<out_dir>/status.json` (`step: "run"`, `rc: 2`, `status: "stopped_cost_cap"`, `failure_class: "COST_CAP_REACHED"`, `cost_cap_reached: true`, `reason: "COST_CAP_REACHED: runtime=<elapsed_s>s * rate=<live_rate>/h >= cap=<cap_units>"`, `live_rate`, `rate_read_at`, `cap_units`, `runtime_seconds`), and `write_outcome_draft` (`scripts/colab/launch_judges.sh`) records `outcome: "stopped_cost_cap"` and `failure_class: "COST_CAP_REACHED"` in `<out_dir>/outcome.draft.json`.
