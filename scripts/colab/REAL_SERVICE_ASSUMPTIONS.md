# Real-Service Assumption Audit (`scripts/colab/launch_judges.sh` & `scripts/colab/vm_judges.py`)

This document audits every interaction the five-judge Colab launcher (`scripts/colab/launch_judges.sh` and `scripts/colab/vm_judges.py`) has with the `colab` CLI (`google-colab-cli` v0.7.4, captured in `tests/fixtures/colab_help.txt` and `tests/fixtures/colab-cli-contract.json`) and the remote Colab Jupyter/IPython runtime.

- **Total rows in assumption table:** **20**
  - **Fake now enforces:** **10**
  - **Left for the stub:** **9** (8 of which also have conservative **guards** in `tests/fixtures/fake_colab.py`, labelled below as guards rather than verified real-service behaviour)
  - **Probe answers it:** **1** (row 20: VM Python 3.15, `uv`, and `pyyaml==6.0.3` sdist build toolchain, answered directly by `--probe` / `RDLAB_STEP=probe` and preflighted at `--step gate` via `check_vm_python_preflight`)

  - `ceil(60,568,837,565 * 115 / 100) = 69,654,163,200` bytes (**`64.87 GiB`**) (`REQUIRED_VM_DISK_BYTES` at `scripts/colab/vm_judges.py:84-88`).
- **Enforcement (`scripts/colab/vm_judges.py:1494-1635`):**
  - `--step gate` checks `shutil.disk_usage` on `/content` and `args.hf_home` (which matches the run's `HF_HOME` via `build_gate_env_args` at `scripts/colab/launch_judges.sh:232-239`, defaulting to `/content/hf_home`), logs `content_free_bytes`, `hf_home_free_bytes`, and `required_bytes` on the `VM_GATE_OK` line, and refuses with `VM_DISK_INSUFFICIENT` (exit code `2`, `status.json` `failure_class="VM_DISK_INSUFFICIENT"`) before any archive or item file is uploaded if either path has fewer than `69,654,163,200` bytes free.

## The part a window runs on

A sealed part built by this repo (`rdlab bakeoff-part`; `waves_and_sealing._PART_FILES`) holds exactly `checksums.txt`, `items.jsonl`, `part.json` and `provenance.jsonl`. No builder writes a part `manifest.json`; until this change the launcher and VM looked only for one, so a real time-one or counted window on a real part refused `PART_MANIFEST_MISSING` (before #66 the VM made up `{"part_id": "pilot-40b"}` instead).

- **What is read.** `launch_judges.sh --part-dir DIR` (`RDLAB_PART_DIR`; default the items file's directory) names the part. The launcher (`check_part_manifest_beside_items`, `scripts/colab/launch_judges.sh:574-617`, `--dry` and live, before any `colab` call) runs `vm_judges.preflight_part_manifest` (`scripts/colab/vm_judges.py:5807`) with the part's `items.jsonl` and the repo's part schema: `part.json` must parse, carry a non-empty `part_id` and a positive `items_count`, match `schema_check.validate(..., "part")`, and hash to the `part.json` line of `checksums.txt`; the part's `items.jsonl` must hash to its `checksums.txt` line and hold `items_count` rows. It stages `part.json` and `checksums.txt` byte-identical to `/content/rdlab_items/` beside the uploaded `items.jsonl`.
- **The binding rule** (`bind_items_to_part`, `scripts/colab/vm_judges.py:5713`). The uploaded file is a projection (`{id, material, claim}`; the upload allow-list refuses a part's own rows). The launcher checks every uploaded row against the part row with the same id (`id`, `material`, `claim` equal), so the projection is verified, not trusted. A counted window (`counted`, `counted-stub`) must upload the whole part in the part's order; a time-one window any subset of it (the VM then takes the first `TIME_ONE_ITEMS_LIMIT` rows). A disagreement refuses `PART_MANIFEST_ITEMS_MISMATCH` naming the field (`items_count`, `id`, `id order`, `material`, `claim`, `items.jsonl sha256`), never the item text.
- **On the VM** (`verify_part_manifest`, `scripts/colab/vm_judges.py:11648`, before the shard manifest, venv sync, device/GPU gate and weights) the same function runs without the part's items: it checks `part.json` against `checksums.txt`, unique ids and the count rule. It does not run the schema check (the kernel imports nothing from the repo). The staged files are deleted after the run and listed in `deleted_items_receipt`.
- **Recorded.** `time_one_summary.json` and `vm_receipt.json` carry `part_identity`: the real `part_id`, `items_count`, `part_json_sha256`, `items_jsonl_sha256` (the part's own items file, from `checksums.txt`), `checksums_sha256`, `is_pilot_40b` and the binding rule. Stub and dryrun windows without a part get an in-memory stub identity (`part_id` "stub"); nothing is written.
- **The burned pilot is named by hash.** `PILOT_40B_PART_JSON_SHA256` and `PILOT_40B_ITEMS_JSONL_SHA256` (`scripts/colab/vm_judges.py:5569-5570`) are the pilot part's `checksums.txt` lines. Its `part_id` is `bakeoff-d-t10-sealed`, which every writer-built part shares, so the id cannot name it. A real time-one window runs the pilot mass check only when both hashes match (`scripts/colab/vm_judges.py:6995`), and records the real `part_id` and hashes; any other part records `not_applicable`.
- **Old receipts.** Receipts written before this change (the 2026-11-03 time-one windows) carry `part_id` `"pilot-40b"` in `pilot_mass_check` and `harness_readouts`. That was a label the VM made up; the part those windows ran on is the one whose `part.json` says `part_id` `bakeoff-d-t10-sealed` (`part.json` SHA-256 `9ae6708e…`). Nothing writes `"pilot-40b"` for a time-one window now.
- **Not changed here.** Lock-check windows carry no `part.json` for their P0a input: their mass check and the P0a validators (`bakeoff_judge.py`) still key on the `pilot-40b` allow-set and the P0a `manifest.json` / `p0a_manifest.json`, and `_resolve_part_id_from_dir` still reads `manifest.json` or `reports/bakeoff_part_report.json`, whose `part_id` for the real pilot is `bakeoff-d-t10-sealed`, outside that allow-set.

6. **Limiting cgroup chain (`read_cgroup_limit_chain` at `scripts/colab/vm_judges.py:2424-2560`):**
   - **Order of paths read:** Starting from `/proc/self/cgroup` (taking the cgroup v2 `0::/<rel_path>` unified entry first, and any cgroup v1 `<id>:memory:/<rel_path>` controller entry second under `<cgroup_root>/memory` or `<cgroup_root>`), `_ancestor_dirs_to_root` walks **bottom-up from the process's own cgroup directory up to `<cgroup_root>`** (e.g. `<cgroup_root>/a/b/c` -> `<cgroup_root>/a/b` -> `<cgroup_root>/a` -> `<cgroup_root>`). For each directory in that walk that exists on disk (`is_dir()`), `read_cgroup_limit_chain` reads `memory.max` (fallback `memory.limit_in_bytes`), `memory.high` (fallback `memory.soft_limit_in_bytes`), `memory.current` (fallback `memory.usage_in_bytes`), and `memory.events` (fallback `memory.oom_control` / `memory.failcnt`).
   - **Null rules:** `read_cgroup_limit_chain` never raises. If `/proc/self/cgroup` is missing, `chain` is `[]` and `nearest_finite_path`, `nearest_finite_memory_max`, and `nearest_finite_memory_current` are all `null` (`None`). Within each existing cgroup directory, any missing or unreadable file yields `null` (`None`) for its field (`memory.max` and `memory.high` preserve raw strings such as `"max"`). The first directory in the bottom-up walk whose `memory.max` is a finite integer (`< 2^60`) sets `nearest_finite_path`, `nearest_finite_memory_max` (int), and `nearest_finite_memory_current` (`memory.current` at that path, or `null` if missing); if every level is `"max"` or missing, all three `nearest_finite_*` fields are `null`. Logged once in `gate_status.json` (`cgroup_limit_chain`), once at run start (`step_start` `unpack` in `progress.jsonl` and `vm_receipt.json`), and via `nearest_finite_cgroup_path`, `nearest_finite_memory_max`, and `nearest_finite_memory_current` on every `judge_download_start`, `judge_download`, `download_failed`, `judge_pass_done`, and `judge_failed` line in `progress.jsonl`.
