# Colab Judge Bake-Off Launcher

Per-window Google Colab launcher (`scripts/colab/launch_judges.sh`) and VM runner (`scripts/colab/vm_judges.py`) for the five-judge bake-off (`mu-judge`, `nemotron-3-nano-4b`, `d3-mini`, `granite-guardian-4.1-8b`, `flow-judge-v0.1`).

Keys and the scorer never leave the rig. Only public item files (`items.jsonl`), weight SHA-256 receipts (`<owner>__<repo>.sha256.json`), and the judge runner code are uploaded to the Colab VM.

**Residual risk (`SIGKILL`):** No shell trap can catch `SIGKILL` (`kill -9`), so if `launch_judges.sh` itself receives `SIGKILL` after `colab new` assigns a VM and before `colab stop` completes, its `EXIT` trap never runs and it leaves an open Colab session that only the background session watcher (when it survives, recording `stop_path: "watcher"`) or a manual `colab sessions` check (`colab stop -s <session>`) stops.

### Item Projection Allow-List (`{id, material, claim}`)

The uploaded `items.jsonl` file is a strict projection containing **only** the three fields `{id, material, claim}` on every JSON object row:
- Before any upload or `--dry` command print on the rig (and again on the VM before the judge run), every row of `items.jsonl` is checked against the exact allow-list `{id, material, claim}`.
- Any extra field (such as `key`, `class`, `verdict`, `key_basis`, `proof_basis`, or `triad_id`), any missing field among `{id, material, claim}`, or any non-object row refuses with `ITEMS_FIELD_NOT_ALLOWED`.
- The refusal message names the offending or missing field(s) and **never** prints any field value.

## Modes and Command Lines

### 1. Session Smoke (`--session-smoke`, CPU at `0.08/h`)

Verifies session open, reconciler lock lifecycle, `colab sessions` row shape, and trap-guaranteed session stop on a CPU runtime without uploading items or pulling weights:

```bash
bash scripts/colab/launch_judges.sh --session-smoke --run-id smoke-01 --out-dir /tmp/rdlab-colab-runs/smoke-01 < /dev/null
```

**Acceptance list (`--session-smoke`):**
- Acquires shared open lock (`/tmp/colab-window-open.lock` via `flock -w 300`).
- Checks `colab sessions` before `colab new` and refuses if `[rdlab-<run-id>]` is already present (`SESSION_NAME_IN_USE`).
- Treats `[colab] No active sessions found on server.` as a CLI message, never a session row.
- Opens CPU session `rdlab-<run-id>`, writes reconciler lock `/tmp/colab-locks/rdlab-<run-id>.lock` with the launcher PID immediately after `colab new` succeeds, and verifies `[rdlab-<run-id>]` is listed in `colab sessions`.
- Stops only `rdlab-<run-id>` in the `EXIT` trap, removes `/tmp/colab-locks/rdlab-<run-id>.lock`, and verifies via `colab sessions` that `[rdlab-<run-id>]` is gone.
- Writes `outcome.draft.json` with `format_verified_on_real_cli` (`true` only when the mid-session listing matched `[<SESSION>] <TOKEN> | <TOKEN>: <TOKEN> | <TOKEN>: <TOKEN> | <TOKEN>: <TOKEN>` and `RDLAB_COLAB_IS_FAKE` was not `1`).

- Writes `outputs-closed.json` (SHA-256 of every output file) on the rig before anything reads keys.
- Runs the rig log guard over every kept log and output file (checking for `sealed_store`, `keys.sealed`, unredacted tokens, and SHA-256 hashed claim n-grams from the uploaded item file without printing claim text).

### 4. Time-One (`--time-one`, `--gpu A100` at `5.30/h`, wall `1500 s`, cap `2.5` units)

Runs all five bake-off judges in one A100 session over 10 burned pilot items in both orders (`AB` and `BA`, 20 calls per judge), each judge in its dedicated CPython 3.15 venv (`venv-judge` for `mu-judge`, `nemotron-3-nano-4b`, `granite-guardian-4.1-8b`, `flow-judge-v0.1`; `venv-d3` for `d3-mini`):

```bash
RDLAB_JUDGE_LOCK_SHA256=608f56ab8eae6852718438366ff0ce74ef6aafb66db75faef034ae0bb5bdcf10 \
RDLAB_D3_LOCK_SHA256=08801f9ac5e3cfb14ce819b051aeef388bea3e564e7b99bddc10d91537ab78e2 \
RDLAB_RECEIPTS_DIR=/path/to/receipts \
RDLAB_ITEMS_FILE=/path/to/inputs/pilot40b-items-projected.jsonl \
RDLAB_PART_DIR=/path/to/part-pilot-40b/part_bakeoff_sealed \
bash scripts/colab/launch_judges.sh --time-one --run-id t1-01 --out-dir /tmp/rdlab-colab-runs/t1-01 < /dev/null
```

`RDLAB_ITEMS_FILE` is the `{id, material, claim}` projection of the part's items (the allow-list above refuses a part's own rows), written by `rdlab bakeoff-project --part-dir <part> --out <file>` outside the part; `RDLAB_PART_DIR` (`--part-dir`) is the sealed part it came from and is required for a real `--time-one` or `--counted` (`PART_MANIFEST_MISSING` without it). Before any `colab` call the launcher checks the part's `part.json` against its schema and `checksums.txt`, every file `checksums.txt` lists, and every uploaded row against the part row with the same id; it then uploads `part.json`, `checksums.txt` and its own binding record (`launcher_part_binding.json`) beside `items.jsonl`. A time-one window may upload any subset of the part; a counted window must upload the whole part in order. The receipts show the launcher's row-by-row check (`part_identity.launcher_binding`, `checked_by: "launcher"`) beside the VM's re-check (`checked_by: "vm"`, `projection_checked: false`); `outcome.draft.json` carries the launcher's record too. A pinned part (the burned pilot, the anchored counted part) must match its pinned hashes (`PART_PIN_MISMATCH`), and a real window needs a frozen part (`PART_NOT_FROZEN`); `frozen_mac` itself is keyed by the sealed store and not verified here. See `REAL_SERVICE_ASSUMPTIONS.md`, "The part a window runs on".

**Declared synthetic time-one (`--synthetic-items` / `RDLAB_SYNTHETIC_ITEMS=1`).** For timing and output-length measurement only without a sealed part, a `--time-one` window may pass `--synthetic-items` (or `RDLAB_SYNTHETIC_ITEMS=1`) with `--items-file` and no `--part-dir`. Allowed with `--time-one` only (`SYNTHETIC_ITEMS_MODE_FORBIDDEN` on launcher/VM in any other mode; `SYNTHETIC_ITEMS_INVALID` on unknown env values; `BAKEOFF_JUDGE_SYNTHETIC_MODE_FORBIDDEN` in `run_bakeoff_judge` when `window_mode` is missing or disallowed; `SYNTHETIC_ITEMS_PART_DIR_FORBIDDEN` with `--part-dir`); every item `id` must start with `synth-` (`SYNTHETIC_ITEMS_ID_PREFIX_INVALID`), and upload allow-list and path hygiene checks still run. No `part.json`, `checksums.txt`, or `launcher_part_binding.json` is staged or uploaded (the launcher logs `[part] synthetic: true (items_file=..., items=...)` to stderr). `window.json`, `vm_receipt.json` (plus `fail_receipt`/`unexpected_receipt` failure writes to `vm_receipt.json` and `receipt.json`), `time_one_summary.json`, and `outcome.draft.json` record `synthetic_items: true` (`false` when unset; `status.json` does not carry `synthetic_items`), and `judge_done` and every output row record `synthetic_items: true` on synthetic runs (omitted when unset so non-synthetic rows and `judge_done` stay unchanged). Synthetic outputs are refused by `check_bakeoff_logprob_mass` / mass readout (`BAKEOFF_LOGPROB_MASS_SYNTHETIC_ITEMS`), `merge_shards` (`MERGE_SYNTHETIC_ITEMS`), and every scorer and counted reader (`BAKEOFF_SCORE_SYNTHETIC_ITEMS`) wherever any marker is present; unreadable files are not treated as synthetic, and real-run readers are unchanged from main.

A counted projection is made the same way, on the rig, into an inputs directory (never into the part or a `sealed_store/`):

```bash
uv run rdlab bakeoff-project \
  --part-dir /path/to/part-anchored-counted-430/part_bakeoff_sealed \
  --out /path/to/colab-runs/inputs/counted430-items-projected.jsonl
```

**Lock-check in two windows.** A lock-check window names its phase, `--lock-check-phase anchors|p0a|all` (no default): `anchors` records the boot gatekeeper's goldens and runs the five judges over the 50 anchors (no P0a; promote its goldens), `p0a` runs P0a only, `all` both. P0a runs one judge at a time, each in its own venv and child process. Make the anchors with `rdlab bakeoff-lockcheck-anchors --part-dir <counted part>/part_bakeoff_sealed --out <inputs>/lc1_anchor_items.jsonl` (the label-blind LC-1 rule; a manifest is written beside it). Every phase takes the same `--anchor-items`, `--p0a-items` / `--p0a-part-dir` and counted source; the default wall is 3600 s (anchors), 5400 s (p0a) or 7200 s (all).

A lock-check window (`--lock-check`) names the burned pilot part for its P0a input with `--p0a-part-dir` (`RDLAB_P0A_PART_DIR`, required in real mode): the launcher checks it is the pilot by its pinned `part.json` / `items.jsonl` SHA-256 (never a `part_id` label), binds `--p0a-items` to it row by row, and uploads its `part.json` and `checksums.txt` as `p0a_part.json` / `p0a_checksums.txt`. The repo bundle is built from the git-tracked files at a clean HEAD (`REPO_TREE_DIRTY` otherwise).

**Three-way pass (`--pass-mode three_way`, the D5a diagnostic).** `--pass-mode` (one of `vm_judges.PASS_MODES`, listed by `launch_judges.sh --help`, or `per_judge`; this paragraph is `three_way`; or `RDLAB_PASS_MODE`; default `binary`, and a binary window is unchanged: nothing extra is forwarded to the VM or the judge child) runs every judge in the window on its 3-way prompt (supported / unsupported / cannot_tell). It is allowed with `--stub` and `--time-one` only (`PASS_MODE_NOT_FOR_MODE` otherwise), an unknown value refuses `PASS_MODE_INVALID`, and a judge without a 3-way prompt (`granite-guardian-4.1-8b`) refuses `BAKEOFF_JUDGE_THREE_WAY_UNSUPPORTED`; all three before `colab new`, so a 3-way window names its judges, e.g. `RDLAB_ONLY_JUDGES=d3-mini,mu-judge,nemotron-3-nano-4b` with `--stub --pass-mode three_way` (CPU verification) or `--time-one --pass-mode three_way` (`--stub --until first_load --pass-mode three_way` with no `RDLAB_ONLY_JUDGES` defaults to `nemotron-3-nano-4b`, which supports 3-way). Each judge writes `rows/<judge>.three_way.jsonl` (`judge_done/<judge>.json` names it in `rows_file` and records `pass_mode`), and `pass_mode` is recorded in `window.json`, `vm_receipt.json`, `time_one_summary.json` and `outcome.draft.json`. On the pinned pilot the mass readout checks A/B/C option mass (>= 0.99) per parsed call for the log-probability judges, and finite, non-negative, positive-sum `choice_probabilities` over the 3 labels for d3-mini. The scorer's public `three_way_pass` carries an aggregate-only `breakdown_by_split` (test, dev, pooled): per-class strict counts, binary-collapsed strict accuracy, the all-3-of-triad rate, order-flip and invalid rates, the 3 x 5 strict outcome counts and top-2 margin quantiles (min, p10, median).

**Three-way, plain-word wording (`--pass-mode three_way_contradicted`, the D5c wording arm).** The same pass, refusals and windows as `three_way`, with one change: the shown words. They come from the per-arm table `THREE_WAY_WORDINGS` in `src/reasoning_dataset_lab/pilot_b/three_way_wording.py`, kept apart from the internal gold labels. The instruction is `Judge the claim against STATE. Which option holds? Claim: <claim>` (d3-mini: `the state`), and the options are shown as `supported`, `contradicted` and `can't tell` (d3-mini's choice keys too). The readout maps `contradicted` back to the internal class for a contradicted claim and `can't tell` to `cannot_tell`, so rows, keys and the scorer keep the internal names and the 3-way scoring applies unchanged. Each judge writes `rows/<judge>.three_way_contradicted.jsonl`; the mass readout and the scorer read it like a `three_way` rows file, and its public summary names the arm with `pass_mode`. Among the original five bake-off judges, only mu-judge, nemotron-3-nano-4b and d3-mini have a wording in this arm, so `flow-judge-v0.1` (as well as granite) refuses `BAKEOFF_JUDGE_THREE_WAY_UNSUPPORTED`. The `three_way` prompts stay byte-identical to 2e6423fd.

**The card and shape (`--card` and `--shape`).** Every real `--time-one`, `--counted` or `--lock-check` window requires `--card A100|G4|L4|T4` (`RDLAB_CARD`; `CARD_REQUIRED` / `CARD_INVALID` before any `colab` call) and `--shape standard|high-mem` (`RDLAB_SHAPE`; `SHAPE_REQUIRED` / `SHAPE_INVALID` before any `colab` call, and `SHAPE_NOT_FOR_CPU` on CPU modes). Right after `colab new`, the launcher checks that the opened session's `Hardware:` and `Shape:` match the requested card (`CARD_MISMATCH`) and shape (`SHAPE_MISMATCH`). **The card type.** A real `--time-one`, `--counted` or `--lock-check` window never assumes a card. After `colab new` the launcher reads the opened session's row in `colab sessions` (`[<session>] <id> | Hardware: <X> | Shape: ... | Variant: ...`), maps its `Hardware:` and `Shape:` to a card type (`vm_judges.SESSION_CARD_TYPES`: `Hardware: A100 | Shape: Standard` -> `A100` (40 GB), `Hardware: A100 | Shape: High-RAM` -> `A100-80` (`--high-mem`, the 80 GB card), `G4`, `L4`, `T4` with `Shape: Standard`; extra spaces are tolerated and anything else (CPU, TPUs `V5E1`/`V6E1`, an unseen card or shape) is refused `CARD_TYPE_UNKNOWN`), logs `CARD_TYPE ... requested=--gpu A100`, and forwards `RDLAB_CARD_TYPE=<card>` to the run cell. It is the session's card, not the `--gpu` request. An unreadable or unknown `Hardware:` is refused `CARD_TYPE_UNKNOWN` right after open, before the alive probe, the gate, any upload or exec (the exit trap stops the session). VM `main` then checks the forwarded card against `nvidia-smi --query-gpu=name` (the driver's binary on the base image) at step `verify_card_type`, after unpack and before venv sync: `CARD_TYPE_UNKNOWN` (not forwarded, or the GPU name unreadable/unmapped) or `CARD_TYPE_MISMATCH`. The receipt records `card_type_check`. Each table entry is pinned to a receipt pairing the same window's session row with its nvidia-smi card (cited in `tests/fixtures/colab-cli-contract.json`); unpaired pairs are refused, and the VM's nvidia-smi check stays the authority. Stub and dryrun runs keep a labelled default (`card_type_source: stub_default`). `--dry` opens nothing: it prints `--env RDLAB_CARD_TYPE=<card-of-opened-session>` and `card_type=<read from colab sessions after open>`.

**Refusal output.** A refusal that comes from a VM subprocess (venv sync, a download or judge child, the boot gatekeeper) keeps the last 40 lines of its stderr (of stdout when stderr is empty), scrubbed, and its exception line: in `status.json` and `vm_receipt.json` as `failure_output_tail` and `exception_line` (the gatekeeper's reason and detail carry both), and in `logs/vm.log` as `VM_RUN_REFUSED`, `VM_REFUSAL_EXCEPTION` and `VM_REFUSAL_OUTPUT_TAIL` lines. The gatekeeper also logs `VM_BOOT_GATEKEEPER_JUDGE`, `VM_BOOT_GATEKEEPER_START` and `VM_BOOT_GATEKEEPER_END` lines and its subprocess as a `VM_SUBPROCESS` line. Download and judge children are captured as ~4 KB tails, so their 40 lines are those of that tail.

**The boot gatekeeper on a local GPU.** `scripts/colab/local_boot_gatekeeper.py` runs the gatekeeper exactly as the VM does (the same subprocess script through `vm_judges.run_boot_gatekeeper_subprocess`, the goldens' prompts and judge, the real transport, offline) against a local HF home, prints each prompt's `output_token_ids_sha256` and whether it matches the golden for `--card-type`, and writes a JSON receipt. It refuses a CPU device (`LOCAL_GATEKEEPER_CPU_REFUSED`) and a run that sees no NVIDIA GPU (`LOCAL_GATEKEEPER_NO_GPU`) before any model load; run it only under a card grant:

```bash
python scripts/colab/local_boot_gatekeeper.py --hf-home /path/to/hf_home --receipts-dir scripts/colab/receipts --card-type RTX5090 --python /path/to/venv-judge/bin/python --out /path/to/local_gatekeeper_receipt.json
```

Exit codes: `0` every prompt matches, or the card type has no golden (`status: no_golden`); `1` a mismatch; `2` refused or the gatekeeper subprocess failed.

`--out` must lie outside the git repository and must not exist unless `--overwrite` is given (`LOCAL_GATEKEEPER_OUT_REFUSED`, before anything runs), so a run can never overwrite `boot_gatekeeper_goldens.json`. The receipt's `subprocess_timings` and the printed `timings` line give the seconds of each phase (`torch_import`, `verify_ready` (re-hashing the weights), `model_load`, `generation_1`, `generation_2`, `total`), the subprocess's measured elapsed seconds and its timeout (`BOOT_GATEKEEPER_SUBPROCESS_TIMEOUT_SECONDS`, 300 s, the VM's). The VM's gatekeeper records the same `subprocess_timings` in its report in `vm_receipt.json` and `status.json`.

- **Pre-plan gates, worst case, and strict Server Edition check (`no_fallback=true`):** Before `offrig_plan`, the host validates the RunPod price cap (`OFFRIG_MAX_PRICE_INVALID`), validates optional `--runpod-max-worst-case-usd` (`OFFRIG_MAX_WORST_CASE_INVALID`), computes the useful-run floor (`compute-run-floor`), refuses incompatible binary/path combinations (`OFFRIG_PATH_INCOMPATIBLE`), verifies the profile `job.image` on window, probe, and session-smoke paths, and on `--counted` / `--lock-check` refuses unless promoted goldens exist for RunPod's own `card_type` (`RUNPOD-RTX-PRO-6000-SERVER`, never reusing Colab `G4` goldens). `offrig_host.py plan_pod` verifies the returned plan GPU list refuses Workstation Edition (`RUNPOD_PLAN_WORKSTATION_REFUSED`). Right after `offrig_plan` and before `offrig_launch`, the launcher prints `RUNPOD_PLAN_WORST_CASE` (`max_hours`, `max_price_hr_usd`, `worst_case_usd`, `worst_case_source`, `local_worst_case_usd`) on stderr and refuses `RUNPOD_WORST_CASE_EXCEEDED` if offrig's `worst_case` exceeds `--runpod-max-worst-case-usd`. Immediately after launch, `offrig_host.py verify-gpu` checks in both `--time-one`/`--counted`/`--lock-check` and `--probe` that both `offrig` pod metadata and in-pod `nvidia-smi` report `NVIDIA RTX PRO 6000 Blackwell Server Edition` with `>= 90,000` MiB VRAM, and VM `verify_vm_card_type` binds `RUNPOD-RTX-PRO-6000-SERVER` against Server Edition on the pod.
- **Full-window watchdog deadline, useful-run floor, bounded fetch, and shutdown:** `offrig_plan` receives explicit `wait_minutes` (`DEFAULT_LAUNCH_WAIT_MINUTES = 20`, `RDLAB_OFFRIG_LAUNCH_WAIT_MINUTES`; launcher readiness timeout defaults to `wait_minutes * 60 + image_pull_setup_seconds`), `max_price_hr` (`DEFAULT_RUNPOD_MAX_PRICE_HR = 2.79`, `RDLAB_RUNPOD_MAX_PRICE_HR`), and computes:
  - `max_hours = ceil((launch_wait_minutes * 60 + image_pull_setup_seconds + wall_seconds + fetch_allowance_seconds + shutdown_reserve_seconds) / 3600.0, 4)` (in `--dry`, `compute-plan-budget` also prints local `worst_case_usd = round(max_hours * max_price_hr, 2)` and cap status with no offrig call).
  - Named defaults in `scripts/colab/offrig_host.py`: `DEFAULT_LAUNCH_WAIT_MINUTES = 20` (`RDLAB_OFFRIG_LAUNCH_WAIT_MINUTES`), `DEFAULT_IMAGE_PULL_SETUP_SECONDS = 900` (`RDLAB_OFFRIG_IMAGE_PULL_SETUP_SECONDS`), `DEFAULT_FETCH_ALLOWANCE_SECONDS = 180` (`RDLAB_OFFRIG_FETCH_ALLOWANCE_SECONDS`), `DEFAULT_SHUTDOWN_RESERVE_SECONDS = 120` (`RDLAB_OFFRIG_SHUTDOWN_RESERVE_SECONDS`), and `DEFAULT_RUNPOD_MAX_PRICE_HR = 2.79` (`RDLAB_RUNPOD_MAX_PRICE_HR`). When `RDLAB_OFFRIG_MIN_RUN_SECONDS` is unset, the minimum useful-run floor is built from named parts (`compute_useful_run_floor_seconds`, default `1225` s): `DEFAULT_VENV_SYNC_ALLOWANCE_SECONDS = 120` (unmeasured conservative allowance for `uv pip sync` of judge/d3 venvs and lazy `venv-vllm` check/sync per `docs/judge-runtime.md`), weight download allowance = `ceil(weight_bytes / (DEFAULT_WEIGHT_DOWNLOAD_RATE_MBPS * 1e6))` (`720` s for `Qwen__Qwen3.6-35B-A3B.sha256.json` `71,926,859,142` B at conservative `100.0` MB/s, or computed from the selected judge receipt(s) in `--receipts-dir`), `DEFAULT_VLLM_START_ALLOWANCE_SECONDS = 180` (unmeasured conservative cold `vllm.LLM` engine startup and weight load), and one-item generation allowance = `max(15, ceil(max_new_tokens / 20.0))` (`205` s at `QWEN36_DEFAULT_MAX_NEW_TOKENS = 4096` / `20.0` tok/s, or `RDLAB_QWEN36_MAX_NEW_TOKENS` / selected `JudgeSpec.max_new_tokens`). `--dry` prints the full floor breakdown (`runpod_min_run_floor`).
  - Right before the `run` step starts, the launcher requires a valid `offrig` UTC `deadline` (`OFFRIG_DEADLINE_INVALID` on empty/unparseable deadlines), checks remaining margin minus `fetch_allowance_seconds + shutdown_reserve_seconds` (`compute_remaining_run_budget_seconds`), refuses `RUNPOD_DEADLINE_EXHAUSTED` (`<= 0`) or `RUNPOD_MIN_RUN_BUDGET_REFUSED` (`< RUNPOD_MIN_RUN_SECONDS`), and tightens `EXEC_TIMEOUT_SECONDS` / `VM_WALL_SECONDS` when setup exceeded its allowance. Each `offrig_get` fetch (`result.tar.gz`, `status.json`, `gate_status.json`, `vm_receipt.json`, `progress.jsonl`, and `logs/vm.log` fallback) is bounded by `remaining-fetch-budget` (falling back on helper error to `min(remaining_allowance, deadline_reserve_margin)` and logging `RUNPOD_FETCH_BUDGET_HELPER_FAILED`).
  - Once `offrig_launch` is attempted for a plan id, every exit path runs `offrig_shutdown` (bounded across main body and trap by `STOP_ATTEMPTS` via `RDLAB_STOP_ATTEMPTS`, default `2`, deferring `SIGTERM`/`SIGINT` until the active shutdown loop finishes and then exiting `143`). `pod_shutdown` is `true` only when `offrig_shutdown` confirms termination (`terminated <pod_id>` or `<pod_id> was already gone`) for the expected pod id. When `offrig_shutdown` answers `"no pod was rented"`, it records `pod_shutdown: null`, `shutdown_failure_class: "RUNPOD_NO_POD_RENTED"`, and one `offrig_status` pod-list read (`shutdown_status_pods`) without emitting `RUNPOD_SHUTDOWN_FAILED_MAY_BILL` (logging both ids on stderr if a pod id had been recorded). Any reply leaving a pod possibly running (`already`, pod mismatch, unreadable, or exhausted attempts) records `pod_shutdown: false`, a named `shutdown_failure_class`, `shutdown_status_pods` from one `offrig_status` read, preserves any earlier `failure_class`/`why`, and writes `RUNPOD_SHUTDOWN_FAILED_MAY_BILL` on stderr.
- **Receipts and USD spend:** `vm_receipt.json` records `host: "runpod"`, `pod_id`, `image_requested` (`ref`, `tag`, `digest`), `image_source: "offrig profile"`, `runtime_environment` (`host_gpu_name`, `driver_version`, `cuda_version`, `python_version` from `venv-vllm`, `system_python_version` from host interpreter, `vllm_version`), `model_download_seconds`, and `model_download_seconds_by_judge`. `outcome.draft.json` records `host: "runpod"`, `venue: "runpod"`, `pod_id`, `offrig_plan_id`, `image_requested`, `image_source: "offrig profile"`, `max_hours`, `max_price_hr_usd`, `worst_case_usd`, `worst_case_usd_source`, `local_worst_case_usd`, `max_worst_case_usd`, `watchdog_deadline`, `cost_usd`, `cost_currency: "USD"`, `cost_per_hr_usd`, `cost_basis` (from `offrig_shutdown` `spent` USD), `pod_shutdown`, `shutdown_attempted`, `shutdown_failure_class`, `shutdown_status_pods`, and `model_download_seconds`.
